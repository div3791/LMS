# 🔥 Mutable vs Immutable — Deep Mental Model Notes

---

# 1️⃣ Core Definition (Interview Ready)

An object is:

- **Immutable** → cannot be changed after creation. Any “modification” creates a new object.
- **Mutable** → can be modified in place without changing its identity.

But that definition alone is shallow.

Real understanding is about:

> Does operation modify existing memory or create new memory?
> 

That’s the real difference.

---

# 2️⃣ Python Memory Model Refresher

Variables are NOT boxes.

Variables are:

> Stickers pointing to objects in heap.
> 

Objects live in heap.

Variables live in namespace dictionaries (frame/global).

Assignment moves sticker.

---

# 3️⃣ Immutable Objects

Examples:

- int
- float
- str
- tuple
- bool

Example:

```python
x=10
x=x+1
```

What happens?

1. Object 10 exists
2. x → 10
3. `x + 1` creates new object 11
4. x sticker moved to 11
5. 10 remains unchanged

Old object is untouched.

---

## 🧠 Real-Life Analogy

Immutable object = Printed book.

If you want to change one word:

You don’t edit page.

You print a new edition.

Original book untouched.

---

# 4️⃣ Mutable Objects

Examples:

- list
- dict
- set
- custom objects

Example:

```python
a= [1,2]
b=a
b.append(3)
```

Memory:

- One list object
- a and b both point to it
- append modifies same object

Result:

```
[1,2,3]
```

---

## 🧠 Real-Life Analogy

Mutable object = Whiteboard.

Two people pointing to same board.

If one writes something,

other sees change immediately.

---

# 5️⃣ Identity vs Equality

```python
a= [1,2]
b= [1,2]

a == b # True (value)
a is b # False (identity)
```

Mutable objects often equal but not identical.

---

# 6️⃣ Why Immutable Matters

Immutable objects:

- Safe to share
- Thread-safe
- Hashable (usually)
- Can be dictionary keys

Mutable objects:

- Dangerous when shared
- Cannot be dict keys
- Cause side-effects

---

# 7️⃣ Dict Key Rule (Important Interview Point)

Dictionary uses hashing.

If key changes after insertion:

- Hash changes
- Dict bucket corrupted
- Key becomes unreachable

So only hashable (stable) objects allowed.

That’s why list cannot be dict key.

---

# 8️⃣ Mutation vs Rebinding

Very important distinction.

## Rebinding

```python
a = [1,2]
a = [3,4]
```

New object created.

Old object untouched.

## Mutation

```python
a = [1,2]
a.append(3)
```

Same object modified.

---

# 9️⃣ + vs += (Important Edge Case)

For list:

- `+` → new object
- `+=` → modifies in-place

For tuple:

- `+=` → creates new object

Because list implements `__iadd__` (in-place add).

Tuple does not.

---

# 1️⃣0️⃣ Function Argument Behavior

```python
def f(lst):
	lst.append(3)
```

Mutation affects caller.

```python
def f(lst):
	lst = lst + [3]
```

Rebinding does NOT affect caller.

This is common backend bug.

---

# 1️⃣1️⃣ Mutable Default Argument Trap

```python
def f(a, bucket=[]):
	bucket.append(a)
	return bucket
```

Default evaluated once at definition time.

Same list reused every call.

Production-level disaster pattern.

Fix:

```python
def f(a, bucket=None):
	if bucket is None:
		bucket= []
```

---

# 1️⃣2️⃣ Small Integer Caching (Advanced Detail)

CPython caches integers from -5 to 256.

So:

```python
a = 256
b = 256

a is b # often True
```

But:

```python
a = 1000
b = 1000

a is b # often False
```

Never use `is` for numeric comparison.

---

# 1️⃣3️⃣ When Immutable Is Actually Mutable (Tricky Case)

Tuple is immutable.

But:

```python
t = ([1,2], 3)
t[0].append(4)
```

Tuple didn’t change.

But inside list mutated.

So immutability is shallow, not deep.

---

# 1️⃣4️⃣ Backend Pitfalls

Real issues I’ve seen:

- Shared config list mutated accidentally
- Mutable default argument leaking data between requests
- Using `+=` thinking it creates new list
- Accidentally modifying request payload object
- Using `is` for integer comparison

These are not theoretical.

---

# 1️⃣5️⃣ Mental Debug Checklist

When debugging strange behavior, ask:

1. Did I mutate shared object?
2. Did I rebind instead of mutate?
3. Is this default argument reused?
4. Is `+=` modifying or creating new?
5. Am I comparing identity instead of value?

If you answer these 5, 90% of bugs solved.

---

# 1️⃣6️⃣ Interview Rapid Answers

Q: Why is tuple hashable but list not?

A: Because tuple is immutable and hash remains stable.

Q: Does immutable mean variable cannot change?

A: No. Variable can rebind. Object cannot mutate.

Q: What happens when you do `x = x + 1`?

A: New object created, x rebinds.

Q: Why are mutable defaults dangerous?

A: Evaluated once; shared state across calls.

Q: Difference between mutation and rebinding?

A: Mutation changes object state; rebinding changes variable reference.

---

# 🧠 Final Mental Model Compression

- Variables are references.
- Immutable → operations create new object.
- Mutable → operations modify same object.
- Closure captures variable reference.
- Default arguments evaluated once.
- Hashable objects must not change.
